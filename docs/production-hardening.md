# Production hardening & migration

Tracks the "Nutri-Matic Production Hardening & Migration Prompts" round:
6 prompts assuming the recommendation engine and its security hardening
(`docs/nutrient-gap-recommendations-hardening.md`) are already done,
focused instead on production deployment, schema evolution, and
operational robustness. Same per-prompt structure as that doc.

## Prompt 1 & 2: real database migrations + safe `updated_at` backfill

Full detail lives in `docs/migrations.md` (the workflow doc every future
migration should follow) — summarised here for the per-prompt record.

**The problem**: this app relied entirely on `Base.metadata.create_all()`
at startup for schema management, plus a long hand-maintained
`ALTER TABLE` block in `DEPLOYMENT.md` for every change to an *existing*
table (`create_all()` only creates missing tables — it never alters
ones that already exist). This wasn't hypothetical: the immediately
preceding hardening round added `DiaryEntry.updated_at`/`MealPlanEntry.
updated_at` to `models.py`, and because `create_all()` can't add a
column to a table that already exists, every real database this app had
ever run against — including this repo's own `docker-compose` Postgres
— was left with a Python model declaring a `NOT NULL` column no
database actually had. That's a genuine, immediate production bug this
round's Alembic adoption fixes, not just a process improvement.

**The fix**: Alembic, with one wrinkle specific to adopting migrations
mid-project — a **baseline** migration (`aac138c38096`) captures the
full schema as it stood immediately before Alembic existed (everything
`create_all()` had ever built, generated by autogenerating against a
genuinely empty database using `models.py` as of the commit *before*
`updated_at` was added). A fresh database runs this baseline for real.
An existing database — which already has these tables via the old
`create_all()` path — is instead told it's already there via `alembic
stamp aac138c38096`, a one-time, required, manual step before its first
Alembic-enabled deploy (attempting to run the baseline's DDL against a
database that already has these tables fails loudly with "relation
already exists," which is the correct failure mode — there's no safe
way to auto-detect "this predates Alembic" from inside a migration).

A second migration (`dba3649596f0`) then safely adds `updated_at` to
both tables for real, using the nullable→backfill→NOT NULL sequence
prompt 2 specifically asked for: add the column nullable (can't fail,
touches no existing row), backfill every existing NULL row to a single
timestamp captured once at the start of the migration (there's no real
prior mutation time to recover, so "the moment this migration ran" is
the most honest available value), then set NOT NULL (safe once nothing
is left NULL). A blunt single-step `ADD COLUMN ... NOT NULL` would have
failed outright against any table with existing rows.

Also fixed along the way: the `pg_trgm` extension `search.py`'s
trigram index depends on used to be created *after* `create_all()` in
`main.py` — backwards for a genuinely fresh database, where the index's
own `CREATE INDEX ... USING gin (name gin_trgm_ops)` would have failed
without the extension existing first. The baseline migration creates
the extension before creating that index, fixing the ordering for real
rather than perpetuating the old opportunistic-and-technically-wrong
sequencing. `main.py` no longer touches schema at all — `Dockerfile`
runs `alembic upgrade head` before starting uvicorn instead.

**Tests**: `tests/test_migrations.py` — four tests against a real,
disposable Postgres database (not SQLite, since the whole point is
verifying real DDL behaviour SQLite's looser constraint handling could
hide a bug behind): fresh-install `upgrade head` creates the full
schema including the `pg_trgm` extension; `downgrade base` tears
everything back down; the documented `stamp`-then-`upgrade` workflow
for a pre-existing database reaches head correctly; and a table with
real pre-existing rows gets them backfilled and NOT NULL, never lost.
Skips automatically if the connecting Postgres role lacks `CREATEDB`
(true of this project's own default local-dev role; always available in
CI). Verified manually end-to-end too, against three disposable
databases in this repo's own `docker-compose` Postgres, before the
automated tests were written — see the commit for the exact commands.

Full backend suite: 957 passed, 4 skipped (the migration tests, at the
default local `DATABASE_URL`), 0 regressions.

## Prompt 3: integer row-version instead of timestamp-based concurrency

**What changed**: `SubstitutionApplyIn.expected_updated_at` (a
timestamp, compared against `DiaryEntry.updated_at`/`MealPlanEntry.
updated_at`) is replaced by `expected_version` (a plain integer,
compared against a new `version` column). `updated_at` itself stays —
it's still useful, honest audit metadata ("when was this last touched")
— it's just no longer the optimistic-concurrency mechanism.

**Why**: an integer equality check has none of a timestamp's
precision/timezone-normalisation edge cases (the previous
implementation needed a dedicated `_as_utc()` helper just to make
naive-vs-aware comparison safe — gone entirely now). It's also the more
conventional mechanism for this pattern, and simpler to reason about:
"does this number match" rather than "does this instant match, modulo
serialisation precision and timezone representation."

**Migration** (`d7819c868cf4`): unlike `updated_at`, this doesn't need
the nullable→backfill→NOT NULL dance — every row's correct backfill
value is the same constant (`1`, "never yet mutated by anything
version-aware"), not a per-row-varying "whenever this row last
changed." A single `ADD COLUMN version INTEGER NOT NULL DEFAULT 1` is
both correct and, on Postgres 11+, a fast metadata-only operation for a
constant default — no table rewrite.

**Increment mechanism**: explicit, not an ORM-level `onupdate` (unlike
`updated_at`). `entry.version += 1` runs alongside the recipe/servings
mutation in `apply_substitution` — the one place that currently mutates
these rows. An `onupdate` callable can't see the row's current value
without a second round-trip, so "increment by 1 from whatever it
currently is" is simpler and exactly as correct written explicitly at
the mutation site. Any future endpoint that mutates a `DiaryEntry`/
`MealPlanEntry` row must remember to bump `version` itself — this is
the same "not automatic across future code" caveat every explicit-
increment version column has anywhere, documented directly on the
model field.

**API surface**: `SubstitutionSuggestionOut`/`SubstitutionSuggestionsOut`
gained `current_entry_version` (replacing `current_entry_updated_at`);
`DiaryEntryOut`/`MealPlanEntryOut` gained `version` alongside the
existing `updated_at`. `apply_substitution`'s two staleness checks are
now: `expected_current_recipe_id` (explicit "this is the specific
recipe I intend to replace" check, also doubling as duplicate-apply
protection) and `expected_version` (the broader "has anything about
this entry changed" check, catching drift `recipe_id` alone wouldn't
— e.g. a hypothetical future edit to `quantity_servings` that left the
recipe untouched). Either mismatch is a 409, same as before.

**Tests**: `test_recommendations_substitutions_api.py` and
`test_hardening_regression_suite.py` — every existing apply-endpoint
test updated to send `expected_version` (read directly off the entry
returned by `POST /api/diary`, exactly the round-trip a real client
would do) instead of `expected_updated_at`. Two categories the prompt
explicitly asks for:

- **Duplicate applies**: `test_duplicate_apply_rejected_on_second_
  attempt` (unchanged in spirit, updated to the new field) — the exact
  same payload sent twice; the second attempt's `expected_version` no
  longer matches after the first one incremented it.
- **Concurrent updates**: a new test,
  `test_concurrent_update_second_writer_rejected_not_silently_
  overwritten`, distinct from a plain replay — two "clients" both read
  the entry at the same version (as two browser tabs genuinely would),
  then race to apply *different* replacements. The first writer wins;
  the second gets 409, and the assertion confirms the first writer's
  change survived untouched rather than being silently clobbered or
  merged.

Also updated: `test_stale_expected_recipe_id_rejected_with_409`'s
timestamp-based sibling test (now `test_stale_expected_version_rejected_
with_409`), and the hardening-suite's equivalent
(`test_stale_expected_version_alone_rejected`).

**Frontend**: `lib/types.ts` (`SubstitutionSuggestion.current_entry_
version`, `SubstitutionSuggestions.current_entry_version`, plus
`version`/`updated_at` added to the `DiaryEntry`/`MealPlanEntry`
interfaces for shape accuracy), `lib/api.ts` (`applySubstitution`'s
`expectedVersion` param, sent as `expected_version`), both `diary/
+page.svelte` and `meal-plan/+page.svelte`'s `applySubstitutionSuggestion`
now read `s.current_entry_version` instead of `s.current_entry_updated_
at`. `vitest run` and `svelte-check` both remain green.

`ci.yml`'s own header comment as the one remaining manual step, with

### Remaining operational risks

- **No monitoring/alerting stack is configured** (no Sentry, Datadog, or
  equivalent). `DEPLOYMENT.md`'s monitoring section names what to watch
  manually; nothing pages anyone automatically. This is the single
  largest gap this round leaves open.
- **CI has never actually run against these changes** — everything
  above was verified by running the equivalent commands locally, not by
  observing a green GitHub Actions run, since nothing in this round has
  been pushed yet.
- **Branch protection is not configured** — "require successful checks
  before merge" (prompt 5's explicit ask) needs a manual, one-time
  GitHub repo-admin action this work deliberately didn't perform.
- **The `version` column's increment is explicit, not automatic** — any
  future endpoint that mutates a `DiaryEntry`/`MealPlanEntry` row must
  remember to bump `version` itself, or optimistic concurrency silently
  stops working for that write path. Documented directly on the model
  field, but there's no structural guard (a test, a lint rule) that
  would catch a future mutation site forgetting it.
  **Resolved** by `docs/operational-hardening.md` prompt 4 —
  `version_id_col` makes SQLAlchemy manage the increment itself for
  every future mutation, not just this one hand-written call site.
- **`SvelteKit`'s adapter is still `adapter-auto`**, a pre-existing,
  already-documented gap (`DEPLOYMENT.md` item 6) — `npm run build`
  prints "Could not detect a supported production environment" as-is.
  Unrelated to this round's scope but still genuinely blocking a real
  deploy until a real adapter is chosen.
  **Resolved** by `docs/operational-hardening.md` prompt 6 —
  `@sveltejs/adapter-vercel` (this repo's actual hosting platform,
  corrected after an initial wrong `adapter-node` guess), see
  `docs/frontend-deployment.md`.
- **The `docker-compose` Postgres and this project's native local-dev
  Postgres are both, as of this session, unstamped** — neither has had
  `alembic stamp aac138c38096` run against it. Both need that one-time
  step before `alembic upgrade head` (or the `Dockerfile`'s automatic
  migration-on-start) will work against them. Deliberately not done as
  part of this work — see the git-safety note in the next paragraph.
- **This round's commits have not been pushed to `origin/main`** as of
  this report, and no live database (including this repo's own running
  `docker-compose` backend container) was migrated or restarted —
  intentional: stamping or migrating a database, and restarting a
  running service, are actions with real operational consequences this
  work stopped short of taking without being asked.
