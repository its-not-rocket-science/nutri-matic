PROMPT 2 — RESOLVE APPROVED FOOD NAMES TO STABLE IDS AND LOCK THE FDC CATALOGUE
=============================================================================

Build a deterministic resolver that converts the 1,139 human-approved target
descriptions into stable target identities using the exact FDC catalogue that
was used for the review.

Required target identity
------------------------

For every approved/replacement mapping retain:

- source row_identifier;
- local Nutri-Matic Food.id;
- USDA fdc_id;
- approved food description as an audit copy;
- FDC data_type;
- review_verdict and match_scope;
- reviewer, review_date and review notes;
- FDC catalogue release/version;
- a deterministic catalogue/import-manifest identifier.

Do not treat local Food.id as externally stable. Store both Food.id and fdc_id.
The importer must verify that they still refer to the same Food row.

Catalogue identity
------------------

Identify how the current FDC ingest records its source release. The project is
known to have used the FoodData Central CSV release dated 2025-12-18, but do not
hard-code that merely from this prompt: verify it from repository configuration,
ingest metadata or the actual catalogue used for review.

If the existing schema has no reliable catalogue manifest, add a small,
general-purpose import/source manifest rather than scattering a release string
through 1,139 rows. It should record at least:

- source/dataset name;
- release/version;
- import date;
- stable checksum(s) for the relevant source/manifest inputs;
- row counts useful for drift detection;
- importer/methodology version.

Resolution rules
----------------

1. Resolve against the exact reviewed catalogue only.
2. A unique exact description match may be proposed automatically.
3. Multiple Food rows with the same name are NOT uniquely resolved. Require a
   deterministic fdc_id decision; never choose query order, minimum Food.id or
   the first row returned.
4. Missing descriptions are unresolved, not silently rematched fuzzily.
5. Replacement verdicts receive the same stable-ID scrutiny as approvals.
6. Prefer an appropriate generic Foundation/SR Legacy food over an arbitrary
   branded record only when that choice is already supported by the signed
   review. Do not rewrite scientific decisions automatically.
7. Output a small exceptions CSV for duplicate, missing or stale targets.
8. Do not allow the final stable mapping to be generated while any exception
   remains unresolved.

The canonical reviewed-mapping artifact must contain fdc_id. It may contain the
local Food.id only as a catalogue-specific convenience; never use Food.id alone
as the durable mapping key.

Tests and acceptance criteria
-----------------------------

- unique description resolves to the correct Food.id + fdc_id;
- duplicate description fails and enters the exception report;
- absent target fails;
- Food.id/fdc_id mismatch fails;
- catalogue release/checksum mismatch fails;
- mapping generation is deterministic across runs;
- all 1,139 rows are accounted for as resolved or explicitly blocked;
- no fuzzy matching is invoked;
- no database writes occur in this prompt.

Report exact totals for unique resolutions, duplicates, missing targets and
manually resolved exceptions. Do not claim completion if exceptions remain.

PROMPT 5 — PRESERVE CENSORED AND NON-NUMERICAL SOURCE OBSERVATIONS
==================================================================

The current adapter skips approximately 245 non-numerical cells such as
"< LOD". Skipping is safer than converting them to zero, but it discards
source provenance and makes coverage harder to describe honestly.

Extend the generic CompoundObservation representation, via an Alembic
migration, so an observation can preserve:

- original reported text;
- numerical original_value when present;
- value qualifier: measured, reported_zero, below_detection_limit,
  below_quantification_limit, trace, not_reported or unparseable;
- detection/quantification limit when explicitly available;
- whether the numerical value was source-reported, converted or imputed;
- original unit and basis where supplied.

Requirements:

- Unknown, blank, trace and < LOD are never converted to zero.
- A literal reported zero remains distinct from absent or below-LOD.
- Retain the exact original cell text.
- Do not invent a detection limit when the workbook supplies none.
- Censored/non-numeric rows may be stored for provenance but must be excluded
  from totals and molar ratios until a separately validated censored-data
  policy exists.
- Preserve backwards compatibility for existing numerical observations.
- Update uniqueness/idempotence tests and workbook reconciliation counts.

Do not put real PhyFoodComp workbook cells into public test fixtures. Use tiny
synthetic fixtures shaped like the source format.

Acceptance tests must cover numeric value, literal zero, < LOD, < LOQ, trace,
blank, unexpected text, missing unit/basis and round-trip preservation.


PROMPT 6 — BUILD A CONSERVATIVE PHYTATE OBSERVATION-SELECTION SERVICE
=====================================================================

Only after Prompts 1-5 are complete, build the downstream service that selects
usable phytate observations for a food/meal. Do not build an absorption model.

Scientific constraints
----------------------

- PHYTC*, IP6, PPI/PPD/PP-, IP5_A_IP6, IP4_A_IP5_A_IP6 and IPSUM are not
  automatically interchangeable.
- Never sum overlapping individual and already-summed fractions.
- Never compare phytate-phosphorus directly with phytic-acid values without a
  documented conversion.
- Do not average analytical methods blindly.
- Prefer a measured, preparation-compatible observation to an analogue or
  category estimate.
- Preserve multiple observations and variability rather than collapsing them
  prematurely into one falsely authoritative number.
- Missing or censored coverage remains unknown.
- Phytate:mineral molar ratios are contextual indicators, not predictions of
  individual absorption.

Implement a versioned, deterministic selection policy returning:

- chosen observation(s) or an explicit no-result reason;
- compound tag/fraction;
- value, unit and basis;
- source and analytical method;
- reviewed match scope/confidence;
- preparation compatibility;
- coverage and uncertainty status;
- methodology/selection-policy version;
- explanation of why an observation was selected or declined.

Do not expose a single food-level phytate value when several incompatible
observations exist and the policy cannot choose defensibly. Return a range or
insufficient_data where appropriate.

If implementing descriptive phytate:zinc or phytate:iron ratios, calculate at
meal level, show the equation and input coverage, and decline when required
inputs are missing or incompatible. Do not modify Nutri-Matic's existing
absorbed-iron or zinc sufficiency calculations in this prompt.

Every service entry point must require and enforce the source-licence surface
from Prompt 4. Tests must prove paid/professional/enterprise consumers cannot
call it under a prohibited surface.
